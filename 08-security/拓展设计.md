# 08-security 拓展设计：从课堂案例再往前一步

课堂案例刻意没做的那几件事（见需求说明第 09 节"范围之外"），这里逐条给出设计方案：要加什么表、加什么接口、动哪些代码、有什么坑。做完基础版之后再挑一两条实现，比重新学一个框架更能体现工程能力。

## 一、登出黑名单（课后作业一，用 Redis）

**现状**：退出登录只清前端 localStorage，令牌本身在过期前（120 分钟）一直有效，拿旧令牌还能调接口。

**方案**：加一个登出接口，把令牌的唯一 id（jti，签发时已写进令牌）扔进 Redis 黑名单，过滤器解析令牌后先查一次黑名单。

```
POST /auth/logout           已登录
Redis key:  jwt:blacklist:{jti} = 1
TTL:        令牌的剩余有效时间（过期了自然就不用拦了）
```

**代码改动**：`JwtAuthenticationFilter` 里解析成功后加一步 `redisTemplate.hasKey(...)`；`AuthController` 加 logout 方法。要注意 TTL 用 `expiresAt - now` 算，别写死，否则黑名单比令牌活得还久，Redis 里堆垃圾。

**为什么用 Redis 不用数据库**：黑名单是"读多写少、自带过期"的数据，正好是 Redis 的地盘，这也是它放在 06-redis 之后讲的原因。

## 二、登录失败次数限制（课后作业一）

**现状**：可以无限次试密码，理论上能爆破。

**方案**：按用户名 + IP 计数，错 5 次锁 10 分钟。

```
Redis key:  login:fail:{username}   INCR 一次 +1
达到 5：    再设一个 login:lock:{username}，TTL 600 秒
登录入口先查 lock 存在就直接回 30002 风格的业务码，不比对密码
```

**坑**：只按用户名锁会被用来恶意锁别人账号（DoS），生产上要用户名 + IP 两个维度取交集；提示文案别写"已锁定"，写"用户名或密码错误或尝试过多"，不给攻击者信息。

## 三、刷新令牌（课后作业一）

**现状**：令牌 120 分钟，过期就得重新登录。

**方案**：双令牌。登录发 access（2 小时）+ refresh（7 天），access 过期前端拿 refresh 换新的。

```
POST /auth/refresh    入参 refreshToken，出参新的 token + tokenType + expiresAt
```

**要点**：① refresh 只能用来换令牌，不能当普通令牌调业务接口（过滤器按令牌里的 claim 区分类型）；② 每次刷新要"旋转"——旧 refresh 作废发新的，并记录已用的 refresh 进 Redis，同一个 refresh 出现第二次说明被复制了，把该用户全部令牌作废。

## 四、按钮级权限（课堂练习四）

**现状**：权限只到菜单和路由，按钮靠页面自己判断。

**方案**：后端已经把 `authorities` 下发在 `/auth/me` 里（`ROLE_` 前缀的角色 + 权限点都有），前端写一个自定义指令就够了：

```
v-permission="'task:review'"     没有该权限点的元素直接不渲染
```

**后端不用改**。注意前端隐藏只是体验，真正的权限判断永远在后端——这条写在需求说明里，面试也常问。

## 五、分页与后端筛选（课堂练习三）

**现状**：`GET /api/tasks` 一次返回全部 28 条，筛选搜索都在前端算。

**方案**：接口加查询参数，返回统一的分页结构。

```
GET /api/tasks?page=1&size=10&status=SUBMITTED&keyword=登录
返回 data: { total, pages, records: [...] }
```

**要点**：① 用 MyBatis-Plus 的 `Page` 对象，`LambdaQueryWrapper` 里 `eq(StringUtils.hasText(status), ...)` 动态拼条件，参数为空不进 where（种子数据里那条"参数为空时不能拼进 where"的评语说的就是这件事）；② `@Min(1)` 校验页码，前端传 0 要挡住；③ **统计卡的平均分不能拿当前页算**，要单独出一个聚合接口或 `selectAvg`，否则翻页时平均分会跳。

## 六、权限点配置化（结课项目方向）

**现状**：角色 → 权限点的映射写死在 `RolePermissions` 这个类里，加角色要改代码重启。

**方案**：加两张表，启动时加载，变更时刷新缓存。

```sql
sec_permission (id, code, name)                 -- 权限点字典
sec_role_permission (role_id, permission_id)    -- 角色-权限点关联
```

**取舍**（需求说明里写过，这里展开）：权限点是代码资产，跟着接口一起评审，留在代码里更清楚；只有"角色能配权限"变成运营需求（教务、助教各种角色要自己调）时才值得建表。真做的话，`RoleService.loadRoleCodes` 旁边加一个 `loadPermissions`，查库结果放本地缓存（Caffeine），管理端改权限后发一个刷新事件清缓存——不改的话每次请求多两条 SQL。

## 建议的实现顺序

1. 先做**登出黑名单**：改动最小（一个接口 + 过滤器一行判断），效果最直观，录屏能现场演示"退出后旧令牌立刻失效"。
2. 再做**登录失败限制**：和黑名单共用一套 Redis 封装。
3. 有余力做**分页**：它和安全的主题无关，但最能补全 CRUD 功底。
